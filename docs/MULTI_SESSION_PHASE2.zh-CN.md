# 第二轮：有界多会话监测（源码实现，未运行验收）

## 先回答：原来能同时检查不同对话吗？

不能。第一轮版本的 IPC 客户端虽然保存多个窗口的活动会话映射，最后只按最新广播序列选出一个 thread。主监控器只有一个 rollout reader；切换时重建状态。它不会把多个对话 token 相加，但也不会持续维护多个后台对话的速度。主浮条的选择仍沿用原来的 IPC/锁定/数据库回退规则，不承诺 IPC 最新广播等于操作系统前台窗口。

## 本轮新增

托盘菜单新增 **“多会话速度 · 近期观察（最多8条）”**。每行显示本地会话短标识、当前标记、模型阶段 TPS 估算、上报 TTFT、状态；当前指主监控器所选或锁定的对话。保留原来的主浮条，不把不同对话的速度或 token 求和。

- 每个 thread 独立 `RolloutReader`、解析状态、去重状态、阶段窗口、TPS、TTFT；多个窗口指向同一 thread 不会增加重复行。
- 使用已有文件 watcher，不额外启动一组 watcher；从当前已解析日志、程序启动后日志的创建/修改/重命名事件发现会话。列表本身不扫描目录、不查询数据库、不读取对话正文用于展示，也不额外读取标题。
- **不是全部历史会话列表**：启动前已存在且之后无写入、未被主监控器选中的会话不会自动出现。无可读日志不补猜速度；不为全部 IPC 窗口预先查找历史文件。
- 已知会话轮询兜底，可继续观察后台写入。窗口关闭不会立即删除其记录；停止写入后隐藏实时 TPS，并保留有限时间的历史 TTFT。IPC 暂时断线不会把列表当成实时窗口清单；Codex 进程离开、监控子系统停止时清空列表。
- 最近十五秒无日志写入，TPS 显示 `--` 并标注历史状态；这只是日志新鲜度策略，不是服务器心跳。正在思考但未写日志也可能显示未知。非当前会话十分钟未观察到更新后淘汰。
- 文件在相同路径变成另一 thread 时移除旧身份；删除/不可读文件不继续冒充实时速度。旧监控实例结束后，其异步结果不会重新填回 UI。
- 列表只在内存里；不保存额外会话内容，不将列表 ID/路径写入常规 debug。短标识仅在本机 UI 显示，截图仍应注意隐私。

## 资源预算及读取修复

- 最多八个后台会话，待发现路径去重队列最多六十四项。队列或 watcher 溢出时 UI 明示可能漏会话，不启动全盘恢复扫描。
- 后台调度至多每秒一轮，每轮最多处理一个事件路径及一个已知会话。按轮转补读；不是每条对话每秒都刷新，也不承诺端到端延迟。
- 每个后台 reader 的尾窗口/单次追加预算为 1 MiB，选中会话 reader 为 4 MiB。另有至多 64 KiB 的会话头检查及 reader 自己的文件头探测；部分行合并会临时分配额外缓冲。**这不是整个应用的总内存/IO硬上限**，解析后的长期去重/事件集合仍有进一步资源审计空间。
- metadata 首行检查统一为有界读取；要求首行换行位于 64 KiB 内且 ID 为 GUID。超过预算、尚未写完或非 GUID 时不识别，等待之后的有效记录；因此不再接受旧逻辑允许的任意字符串 ID。身份来自第一条 Desktop session metadata，不从正文推断。
- 达到尾窗口预算但没有历史 usage 时保持未知/已有数据库基线，不扩大到整个日志文件；可能牺牲较旧回合恢复能力，优先不编造数据。具体超限警告目前被常规 debug 的整栏脱敏规则隐藏，UI 只体现为数据不足/未知，这是已知诊断限制。
- 修复半行重复拼接：读取 offset 现在指向已读字节末尾，pending 独立等待后续字节，不重新读取并再次拼入同一前缀。
- 重新初始化更换完整解析状态，清除私有去重和来源字段；损坏形状记录不会终止后续记录解析。重新初始化和部分日志缺失仍应通过合成运行测试验证。

TPS 继续是包含推理的模型阶段估算，不是逐 token 解码测速；阶段边界可能推导而来。TTFT 仅来自上游上报，缺失不估造；新回合只清除本会话的旧 TTFT。
